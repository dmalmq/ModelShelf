ModelShelf · Draft 1 · Planning only

A complete building review.

Open a combined model delivery, check its information, inspect grouped findings, and compare the next revision.

11 implementation tasks · 2 waves · 4 final checks. Application code has not changed during planning.

Rust owns the application. A local IfcOpenShell/IfcTester worker handles IFC interpretation and checks. Next.js provides the reviewer interface.

One building view

Architecture, structure, and services together. Filter by source, discipline, floor, and object type. Select, isolate, and inspect affected objects.

Findings people can act on

Priority first, then category. Repeated violations become one finding with an affected-object count. Incomplete checks stay visible.

Traceable revisions

Reuse unchanged models. Every run pins exact input revisions and pack settings. Compare changes with a shared camera and before/after properties.

Honest comparison

IDs track identity; hashes track state. Ambiguous matches stay uncertain. A shape fingerprint difference is a representation change, not proof of a physical difference.

Scope
### Must have Build a local, single-user prototype for a client-side BIM reviewer. Keep the working name ModelShelf. The physical workspace remains rockling; the Orca display name is ModelShelf. The reviewer creates a delivery containing architectural, structural, and services revisions, checks it against a versioned pack, navigates grouped findings in a combined 3D view, and compares two deliveries. Every result identifies its exact input revisions and check-pack version. Approved architecture: - Approved reusable-module amendment: [module ownership and contracts](../../docs/adr/0001-reusable-model-modules.md). It supersedes earlier drafts that expose bare IFC IDs as the reusable viewer interface. Shared contracts and one reusable viewer package are required; no new network services or native RVT/PLN support are added. - Rust/Axum owns HTTP, revisions, SQLite persistence, local content-addressed file storage, job scheduling, grouping, fingerprints, and comparison. - A local Python worker using IfcOpenShell and IfcTester owns authoritative IFC interpretation and IDS evaluation. Run it as a subprocess with a versioned JSON file protocol, not a public service. Pin tested dependency versions in a lockfile during implementation. - Next.js/React owns ModelShelf UI and consumes the public React export of packages/model-viewer. Its rendering core is framework-independent, and packages/model-contracts provides generated shared payloads. Reuse existing versions and styling unless a measured incompatibility requires an update. Three.js and web-ifc are the initial viewer path, with IFC processing in a Web Worker. - Keep existing Rust libraries and tests as research/reference code where useful. The incomplete custom IDS engine must not produce production scorecards. Refactor fingerprint/modeldiff consumers to accept the worker's normalized snapshots instead of relying on custom IFC interpretation. - SQLite and filesystem storage are sufficient for the local prototype. One active heavy processing job at a time. No Redis, Kubernetes, cloud deployment, or authentication platform. Domain decisions: - SourceModel is a persistent project-owned input such as Architecture East or Mechanical. Discipline is metadata, not its identity. - ModelRevision is immutable and belongs to one SourceModel. It records content hash, schema, source file, processing versions, status, and artifacts. - Delivery is a dated manifest of source-model revision references. A new delivery can reuse unchanged revisions. One revision per SourceModel per delivery; multiple SourceModels may share a discipline. - Run snapshots delivery membership and pack version in one transaction before processing. Store run_models rows with revision IDs and hashes. Never reconstruct historical inputs from a mutable delivery. - ObjectOccurrence is revision-specific. A public viewer reference includes opaque revisionId and objectId. IFC expressId and optional GlobalId stay in a source mapping shared by the worker and browser adapter. A persistent object match is scoped to SourceModel and only considered exact when the GlobalId is unique on both sides. - Duplicate/missing/changed IDs are unresolved unless an explicit heuristic candidate is shown. Do not mark arbitrary pairings exact. Splits/merges remain unresolved in this prototype. - Checks apply to explicitly selected SourceModels or disciplines. Evaluate per file and aggregate results; cross-model geometric rules are excluded. An intentionally excluded structural model does not create a missing-space failure. - PackVersion contains IDS, rule metadata, source references, scope, and a supported-rule profile. Severity/category metadata is outside the IDS XML but part of the immutable pack digest. User experience: - Project shelf with delivery dates, included models, processing status, and run history. - Review screen with a findings panel and combined viewer. Filters include source model, discipline, storey, object type, severity, and category. - Severity bands precede categories. One row per distinct failed requirement; instances expand beneath it. Counts identify distinct objects where labelled as object totals, rather than adding duplicate memberships. - A finding shows source requirement, expected/actual information, scope, affected count, and processing limitations. Selecting it can highlight all affected objects, not only the first embedded page of 25. - Viewer supports selection, framing, isolation/reset, transparency, section cut, model visibility, and property inspection. Textual findings remain usable if geometry fails. - Comparison includes added/removed objects, property changes, movement/rotation, shape fingerprints, and new/resolved/persistent findings. Use a shared camera with base/head toggle and change overlay. Display revision-qualified object details. - Finding comparisons require the same pack version, scope semantics, and identical persisted check-profile digests. Otherwise ask for a rerun under matching settings; do not label engine changes model regressions. - Use text as well as color for severity, change kinds, and incomplete results. Preserve Japanese property labels. Fingerprint policy: - Rust computes independent property, placement, shape, and combined BLAKE3 digests from normalized worker output. Store full digests internally. - Normalize measures according to their dimensions and explicit units, including length, area, and volume. Sort unordered collections deterministically and retain meaningful list ordering. - Shape fingerprint uses normalized local-coordinate tessellated triangles from fixed IfcOpenShell settings. Canonicalize triangle ordering and vertex cycles, not topology. Placement is separate and includes rotation. - Initially round lengths to 0.1 mm and directions to 1e-6; version these settings. Quantization is not a guarantee that every pair within a tolerance shares a hash. Flag unsupported representations and do not use missing geometry as proof of unchanged shape. - A different tessellation can still change the shape fingerprint. Label it 'Shape representation changed', not proof of physical geometry change across exporters. - Recompute both sides under the same fingerprint profile before comparison. Cache by model hash plus worker/settings version. ### Must NOT have (guardrails, anti-slop, scope boundaries) No Revit add-in/write-back, arbitrary Excel-to-IDS conversion, clash/code-compliance engine, regulatory approval labels, BCF round-trip, billing, production multi-tenancy, automated fuzzy identity acceptance, or public redistribution of restricted sample files. No product implementation during this planning turn.
Verification strategy
Test decision: focused regression tests for the confirmed identity/unit/evidence bugs, then integration tests with each feature. Use existing cargo tests, Python worker tests, and browser-driven QA. Do not weaken the existing tests to hide failures. New verification entrypoints named below are deliverables, not commands that already exist. Use .omo/evidence/modelshelf-prototype/ for logs, screenshots, timings, and manifests. Keep third-party inputs and user data out of commits. Record CPU/GPU, RAM, browser version, model bytes, product count, and triangles for performance checks. Provisional acceptance on the recorded local machine: at least 30 FPS median during a scripted orbit, p95 selection response below 200 ms after load, filtering below 500 ms, and no UI-thread tasks above 200 ms during parsing. Cold initial geometry should be usable within 15 seconds on the selected three-discipline demo. Record peaks and failures honestly; these are prototype targets, not measured claims or universal hardware promises. Verify a clean empty data directory, restart persistence, duplicate uploads, missing IFC geometry, corrupt input, worker crash, unsupported rule, mixed model units, duplicate GlobalIds, and more than 100 affected objects. A failed worker must never yield a clean scorecard.

A reviewer can run the prototype locally, open a combined building, filter models, run a source-backed pack, inspect grouped findings, select all affected objects, compare deliveries, and explain why a finding appeared or disappeared. Restarting the service preserves inputs and results. Known incomplete work is visible rather than counted as success.
