# Synthetic diff/checking fixtures

`base.ifc` and `head.ifc` are a self-authored (not downloaded) A/B delivery
pair, generated by [`scripts/generate-demo-fixtures.py`](../../../scripts/generate-demo-fixtures.py)
via `ifcopenshell`'s Python API — a small, real, valid IFC4 project with
`IfcWall` occurrences built specifically to exercise `crates/modeldiff` and
the checker's finding-grouping end to end, against real parsed files rather
than in-memory Rust structs. [`oracle.json`](oracle.json) lists, per category,
the GlobalIds involved and the diff classification a consumer should expect —
regenerate and re-check independently with:

```
uv run --project services/ifc-worker python scripts/generate-demo-fixtures.py
uv run --project services/ifc-worker python scripts/check-demo-oracle.py --prove-regen
```

`--output-dir` writes elsewhere so tests can regenerate without touching the checked-in baseline. GUIDs and IFC timestamps come from `--seed` (default `modelshelf-demo-fixtures-v1`).

## Two real things this fixture found while it was being built

**A real bug, fixed as a prerequisite.** `crates/modeldiff/src/heuristic.rs`'s
`origin()` read a placement array as `[R,R,R,T, R,R,R,T, R,R,R,T]` (translation
interleaved into a row-major 3x4), indexing `[3, 7, 11]`. The actual, documented
layout `ifc_model::Transform::to_array12()` produces is three axis vectors
then the origin — `[xx,xy,xz, yx,yy,yz, zx,zy,zz, ox,oy,oz]` — so the real
origin lives at `[9, 10, 11]`. The mismatch was invisible to
`crates/modeldiff`'s own unit tests because its test helper
(`crates/modeldiff/tests/diff.rs::placement_at`) constructed placement arrays
by hand in the *same* wrong convention the buggy code assumed — internally
consistent, but never checked against what a real parsed IFC file actually
produces. Building this fixture and running it through the real
`ifc_model → fingerprint → modeldiff` pipeline surfaced it immediately: a real
500 mm translation (the "Moved" category) was reported `unchanged`
("sub-threshold displacement 0.000000 m"), and a pure rotation with zero
translation (the "Rotated" category) was reported `moved` because the
mis-indexed origin jumped when the axes rotated. Those two results inverted
the origin-only classifier of that era. Fixed by correcting `origin()`'s
indices and updating `placement_at()`'s test helper to the correct layout.
All 14 pre-existing `modeldiff` tests still pass unchanged in behavior, now
against a correctly-encoded fixture
(`.omo/evidence/modelshelf-prototype/task-5/modeldiff-tests-after-fix.txt`).
The live rotation contract is in the next section, not in that bug report.

**The rotation decision.** After that origin-index fix, a pure rotation about
an object's own origin used to classify as `unchanged` because `classify_pair`
only measured origin-to-origin distance. The placement digest already hashed
the full axis set, so the rotation was visible as a fingerprint change and
then forgiven as a zero-metre displacement. Ticket 34 stores the worker-v2
row-major 3x4 on `IdentitySide` and classifies a differing basis as `moved`
with a note `placement basis changed (max |Δcosine| …)`. Sub-threshold
forgiveness still requires an identical basis and origin displacement at or
below `move_threshold_m`. `ChangeKind` stays at seven values. There is no
`Rotated` kind.

**A real modeling lesson.** The "Added"/"Removed" categories initially used
the same generic block size as everything else. Since `crates/modeldiff`'s
heuristic matcher scores candidate pairs as 40% shape + 30% placement + 20%
properties + 10% name, two unrelated walls that happen to share a shape and
have no properties can clear the 0.6 confidence floor on shape+properties
alone (0.60 exactly) and get paired as "the same object, unchanged" instead of
a clean add + remove — which is exactly what happened on the first attempt.
Fixed by giving `Removed-*`/`Added-*` each a block size unique across the
entire fixture, which is now documented as a requirement for every category
in the generator script's own module docstring.
